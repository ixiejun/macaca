## ADDED Requirements

### Requirement: Macaca SHALL provide a supplier-grade Foundation Random Pack

Macaca SHALL provide `pack.foundation.random.v1` as a provider-neutral,
serviceized randomness pack for cryptographic bytes, random fill, bounded
integers, UUID v4, nonces, tokens, deterministic test streams, entropy health,
and provider capability diagnostics.

#### Scenario: Application declares random access
- **WHEN** an application declares `pack.foundation.random.v1` with required
  permission scopes
- **THEN** admission SHALL validate pack id, lifecycle, permission scopes, policy
  bounds, service mappings, command schemas, and provider capability requirements
- **AND** admission SHALL produce an effective capability report with callable,
  denied, unsupported, and unavailable command states

#### Scenario: Required random provider is unavailable
- **WHEN** `pack.foundation.random.v1` is required but no admitted provider can
  satisfy declared commands
- **THEN** application readiness SHALL be blocked with structured unavailable or
  entropy-unavailable diagnostics
- **AND** Macaca SHALL NOT crash, hang, silently fall back to insecure
  pseudo-randomness, or fake success

#### Scenario: Deterministic test support is unavailable
- **WHEN** deterministic test stream commands are unavailable or not policy
  approved
- **THEN** SDK discovery SHALL report deterministic commands as denied or
  unavailable
- **AND** SDK helpers and WASM host imports SHALL refuse to build callable
  deterministic random service calls

### Requirement: Random commands SHALL use typed canonical service calls

Every `random.*` operation SHALL be represented as a typed command/result DTO
and SHALL traverse the canonical service runtime path with trace, policy,
resource, entitlement, health, snapshot, and structured error behavior.

#### Scenario: Random bytes command succeeds
- **WHEN** a declared and policy-allowed `random.bytes` command is invoked with a
  valid length, purpose, and strength class
- **THEN** Macaca SHALL route the command through SDK/facade helpers into the
  random service provider
- **AND** it SHALL emit sanitized policy, service-call, result, and replay events
  with length, purpose, strength, provider class, and stable trace identifiers
  without logging generated bytes

#### Scenario: Bounded integer command is unsupported
- **WHEN** `random.integer` is requested but the provider cannot guarantee
  bias-free bounded integer generation
- **THEN** Macaca SHALL return a typed unsupported result
- **AND** it SHALL NOT use modulo-biased fallback behavior

#### Scenario: Deterministic stream is denied before side effects
- **WHEN** `random.test_stream_create` is requested outside a policy-approved
  test or replay context
- **THEN** Macaca SHALL return a typed denied result before creating a
  deterministic stream
- **AND** audit evidence SHALL include only bounded reason codes and policy
  metadata, not raw seeds

### Requirement: Random generation SHALL separate cryptographic and deterministic contexts

`pack.foundation.random.v1` SHALL expose explicit DTOs for strength class,
purpose, byte length, token alphabet, UUID version, seed references, stream
references, and entropy health. It SHALL NOT expose raw provider RNG objects to
applications.

#### Scenario: Application requests production token
- **WHEN** an application invokes `random.token` for production execution
- **THEN** Macaca SHALL require cryptographic or strong provider capability,
  validate token length and alphabet, and return only the generated token result
  to the caller
- **AND** traces, audit records, snapshots, and diagnostics SHALL NOT contain the
  generated token value

#### Scenario: Application requests raw seed logging
- **WHEN** an application or provider attempts to place a raw deterministic seed
  in trace, audit, snapshot, or diagnostics
- **THEN** Macaca SHALL redact or reject the record
- **AND** only opaque seed references and stream positions SHALL be observable

### Requirement: Random health, snapshots, and replay SHALL be bounded and sanitized

Macaca SHALL bound and sanitize entropy health, provider capability diagnostics,
deterministic stream metadata, traces, audit records, and snapshots for
`pack.foundation.random.v1`.

#### Scenario: Entropy health is recorded
- **WHEN** `random.entropy_health` or service snapshot records provider health
- **THEN** Macaca SHALL include provider class, CSPRNG availability, blocking
  risk, max byte request, UUID support, integer support, deterministic support,
  rate-limit counters, and unavailable reasons
- **AND** it SHALL exclude generated values, raw seeds, raw provider payloads,
  credentials, private keys, and raw secret material

#### Scenario: Replay inspects random decision
- **WHEN** audit replay inspects a random-dependent decision
- **THEN** replay evidence SHALL include command name, purpose, strength, length,
  provider class, policy decision, and trace identifiers
- **AND** replay SHALL NOT require generated random bytes unless the command used
  an approved deterministic test stream

### Requirement: Random implementation SHALL preserve Macaca boundaries

The random implementation SHALL remain owned by the random system service and
replaceable providers. The microkernel, SDK, shells, and generic application
framework SHALL remain provider-neutral and free of application-specific random
routing.

#### Scenario: Boundary gates scan random implementation
- **WHEN** dependency, no-direct-provider-call, and canonical execution-path
  gates scan the implementation
- **THEN** they SHALL find no concrete RNG provider imports in the microkernel,
  SDK, shells, or generic application framework
- **AND** all callable operations SHALL be reachable only through descriptor-owned
  service registrations and typed service commands

#### Scenario: WASM app uses random host imports
- **WHEN** a WASM application invokes random host imports
- **THEN** the host imports SHALL route through the same `random.*` service
  command path used by SDK and YAML applications
- **AND** WASM code SHALL NOT receive raw host RNG handles or bypass policy

### Requirement: Random pack completion SHALL include developer documentation

The `pack.foundation.random.v1` proposal SHALL NOT be marked complete until the
detailed developer guide exists and is linked from SDK discovery metadata.

#### Scenario: Developer reads random pack documentation
- **WHEN** a developer opens `docs/developer-packs/foundation/random.md`
- **THEN** the guide SHALL document manifest declaration, cryptographic versus
  deterministic randomness, permission scopes, policy defaults, resource/rate
  limits, command DTOs, result DTOs, error DTOs, UUID/nonce/token guidance,
  integer bias avoidance, deterministic test streams, unavailable diagnostics,
  provider replacement, trace/audit fields, and examples
- **AND** examples SHALL use generic data and SHALL NOT hardcode application
  business logic, provider names, credentials, or workflow-specific token formats
