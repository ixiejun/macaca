# 架构坏味道分析报告

**项目：** Macaca Agent OS (`macaca/`)
**范围：** 整个 Rust workspace，加架构文档和 OpenSpec 目录清单；已排除生成物和构建产物
**日期：** 2026-06-18 11:24 Asia/Shanghai
**分析器：** smell skill（本地静态扫描模式）

---

## 执行摘要

Macaca 当前呈现的是一个**微内核导向的模块化单体架构**：foundation crate 定义协议、持久化和 IPC 契约；kernel crate 持有核心原语；services crate 承载能力族；runtime-host 负责 provider 组合；SDK 暴露 facade client；shell 负责 HTTP/CLI 适配。整体上，这与 Macaca 的架构治理模型一致，不属于 Big Ball of Mud。

最高价值的坏味道不是“没有架构”，而是**适配层和组合层仍残留一部分语义所有权**。`macaca-web` 中仍有任务分解启发式逻辑和 app/session 投影逻辑，`macaca-runtime-host` 则承载了大量 provider 实现和编排模块。这些在演进过程中可以理解，但也是最容易重新引入服务化边界回退的区域。

代码库的边界测试非常强，包含微内核、服务化、依赖方向等 gate。但部分测试文件已经变成较大的策略集合，运行时安全性较好，演进维护成本偏高：修改一条边界规则，可能需要阅读数百行甚至上千行混合 fixture 和断言的测试代码。

---

## 识别到的架构风格

**架构风格：** 微内核 + 服务运行时 + 应用 ABI，以 Rust workspace 模块化单体实现。

### 架构期望与现实

| 期望 | 现实 | 状态 |
|------|------|------|
| Kernel 小而中立，不依赖具体 provider | `macaca-kernel` 约 4,154 行，主要依赖 proto/ipc，并有 purity gate 保护 | 良好 |
| 服务层拥有能力语义 | 大多数能力族位于 `crates/services/*`，广泛使用 service descriptor 和 command/result DTO | 良好 |
| Shell 只做适配 | `macaca-web` 约 37,832 行，仍包含 decomposition、projection 和兼容逻辑 | 警告 |
| Runtime host 只做 provider 组合，不演化成领域对象 | `macaca-runtime-host` 约 89,539 行、425 个 Rust 文件，包含大量 provider 模块 | 警告 |
| 源文件保持在治理上限内 | 未发现生产 Rust 文件超过 500 行，但大量文件处于 450-499 行区间 | 警告 |
| 架构决策可追踪 | OpenSpec 和 integration gate 很完整，但历史变更目录体量很大 | 良好，但有归档债务 |

## 按类别汇总

### 严重问题

1. `macaca-web` 中仍有 shell 层任务分解语义，如果继续增长，会破坏 shell 边界。
2. `macaca-runtime-host` 是非常大的组合和 provider 枢纽，虽然职责拆分存在，但 crate 级耦合风险较高。

### 警告

1. 很多模块刚好贴近 500 行治理上限，后续改动空间不足。
2. 边界测试很强，但部分测试文件已经过大。
3. 部分查询路径仍依赖对 manifest、skill、alias、task、memory entry 的重复线性扫描。
4. protocol DTO 模块偏大，有演化成共享数据倾倒区的风险。
5. 少量进程级静态 registry/lock 需要更明确的生命周期说明。

### 建议

1. 将 shell 启发式逻辑迁移到 service-backed strategy/command 路径。
2. 将 runtime-host provider 模块按 Command Handler、Descriptor、State、Tests 拆分。
3. 增加轻量静态 smell gate，覆盖文件大小余量、shell 语义所有权和热点线性扫描。

## 详细发现

### Finding #1：Shell 层拥有任务分解启发式逻辑

- **类别：** Architecture
- **严重性：** Critical
- **反模式：** 违反层边界
- **位置：** `crates/shells/macaca-web/src/loop_manager/decomposition_adapter.rs:133`
- **违反原则：** 微内核 shell 边界、单一职责原则
- **描述：** shell 层包含基于关键词的任务分类逻辑，例如 `research`、`analysis`、`write`、`review` 等。即使这是兼容路径，它仍然属于语义规划行为。按稳定 Macaca 模型，shell 可以解析输入和渲染状态，但 task planning/decomposition 应由 Task/Autonomy service 通过 typed command 拥有。
- **证据：** 静态扫描发现 `loop_manager/decomposition_adapter.rs` 中存在连续的 `text.contains(...)` 分支。
- **建议：** 引入由 task/autonomy service 拥有的 `TaskDecompositionStrategy` 或 service-backed Command 路径。`macaca-web` 只提交 decomposition 请求，并渲染返回的 plan/task board。

### Finding #2：Runtime Host 是耦合热点

- **类别：** Architecture / Cohesion
- **严重性：** Critical
- **反模式：** God Module 风险
- **位置：** `crates/runtime/macaca-runtime-host`
- **违反原则：** 单一职责原则、稳定依赖原则
- **描述：** `macaca-runtime-host` 约 89,539 行、425 个 Rust 文件。作为 provider/composition hub，这个体量有历史合理性，但它集中承载 application execution、services、plugins、WASM、tools、payments、execution control、diagnostics 及大量 provider tests。这里的问题不是单个巨型文件，而是 crate 级别的耦合热点。
- **证据：** 模块扫描显示 `crates/runtime/macaca-runtime-host` 是全项目最大 crate，显著大于其他模块。
- **建议：** 如果它继续作为批准的 composition root，可以保留 crate 形态，但内部 provider family 应按 Descriptor、State、Command Handler、Adapter、Test Fixtures 清晰分层。对已经成熟稳定的 service family，可在 public contract 稳定后考虑提取为独立 service crate。

### Finding #3：大量文件贴近治理上限

- **类别：** Cohesion / Code
- **严重性：** Warning
- **反模式：** God Object 早期信号
- **位置示例：** `evm_service_provider.rs:499`、`application_execution_service_provider.rs:498`、`execution_control_session_loop.rs:497`、`config_service_commands.rs:497`、`application_execution_client.rs:490`
- **违反原则：** 单一职责、可维护性
- **描述：** 项目规则要求 Rust 文件不超过 500 行。扫描未发现生产源码超过上限，但很多文件在 450-499 行之间。这通常说明模块已经接近拆分边界，继续追加行为容易以“压线合规”替代真正的职责拆分。
- **证据：** 静态行数扫描发现超过 50 个 Rust 文件在 450 行以上。
- **建议：** 增加 450 行软警告 gate。凡是在这些文件中新增行为，应先要求拆分计划。优先使用 Extract Module / Command Handler 拆分，而不是简单移动空行或注释。

### Finding #4：边界测试文件过大

- **类别：** Testing
- **严重性：** Warning
- **反模式：** Test God Object
- **位置：** `crates/tests/macaca-integration-tests/tests/serviceization_escape_hatches.rs:1116`、`autonomy_scheduler_heartbeat_services.rs:694`、`protocol_service_dependency_boundaries/gate.rs:560`
- **违反原则：** 测试可维护性
- **描述：** 边界测试是项目优势，但部分文件将多类规则、fixture、断言混在一起。失败定位和边界演进成本会逐步升高。
- **证据：** 测试行数扫描发现多个 integration test 文件超过 500 行，其中一个超过 1,100 行。
- **建议：** 按策略类别拆分测试：kernel purity、service allowlist、shell adapter constraints、SDK provider-construction constraints、trace/audit requirements。共享 fixture 放入小型 support module。

### Finding #5：热点路径存在重复线性扫描

- **类别：** Complexity
- **严重性：** Warning
- **反模式：** Repeated Linear Scan / 错误数据结构
- **位置：** `skill_mcp_mapping_registry.rs:185`、`routes/shared.rs:137`、`capability_catalog/alias_resolution.rs:174`、`loop_manager/decomposition_adapter.rs:377`、`memory/manager.rs:79`
- **违反原则：** 性能可扩展性
- **描述：** 多处对 descriptor、manifest、alias、task、memory row 使用 `.iter().find(...)`、`.contains(...)` 或嵌套 `.any(...)`。其中一部分是冷路径或小 N 路径，不一定需要立即优化；但 catalog、session、task board 刷新路径会随 installed apps、skills、agents、event history 增长。
- **证据：** complexity scan 在 registry、route projection、alias resolution、task dependency selection 和 memory aggregation 中发现重复 membership 检查。
- **建议：** 对每请求、每事件、每 task-board refresh 调用的路径，构造 request-local `HashSet` / `HashMap` 索引。若 UI 顺序重要，应单独保留 ordering。

### Finding #6：Protocol DTO 模块变得过于密集

- **类别：** Design
- **严重性：** Warning
- **反模式：** 共享数据倾倒区
- **位置：** `crates/foundation/macaca-proto/src/memory_service.rs:483`、`scheduled_agent_task_service/mod.rs:480`、`application_abi.rs:434`
- **违反原则：** 接口隔离原则
- **描述：** `macaca-proto` 是共享契约的正确位置，但部分 protocol 模块已经很大，包含大量 command/result/state。如果行为、校验和兼容策略继续累积，DTO 模块可能变成事实上的语义所有者。
- **证据：** `macaca-proto` 约 30,642 行、162 个文件，多个 DTO 模块接近 500 行。
- **建议：** 按 command family 拆分 protocol 模块。proto 内仅保留 validation、redaction、serialization 相关 helper；业务状态迁移应留在 service 或 kernel primitive 中。

### Finding #7：进程级静态状态需要明确生命周期边界

- **类别：** Coupling / Design
- **严重性：** Warning
- **反模式：** Common Coupling / Static Cling
- **位置：** `macaca-web/src/session/persistence.rs:39`、`macaca-agent/src/in_process_execution.rs:77`、`macaca-driver/src/sdk.rs:36`
- **违反原则：** 显式依赖管理
- **描述：** 静态 registry 和 lock 在进程内集成场景中有时是合理的，但对于 24/7 自主运行 OS，需要清晰的 reset、测试隔离、重启语义。否则它们会成为隐藏依赖，影响多租户、多 workspace 或长生命周期运行。
- **证据：** 静态扫描发现 session lock、in-process execution、driver SDK 中存在 `OnceLock` 或 static mutex registry 模式。
- **建议：** 为每个 static 补充生命周期、所有权和 reset 策略说明。能通过 composition-root state 显式传递的，优先显式传递；缺省状态使用 Null Object 或 unavailable provider。

### Finding #8：兼容路径中仍有文本/名称驱动路由

- **类别：** Design / Naming
- **严重性：** Suggestion
- **反模式：** Primitive Obsession / Magic Strings
- **位置：** `skill_mcp_mapping_registry.rs:102`、`decomposition_adapter.rs:133`，以及部分测试中的 provider-neutral 字符串断言
- **违反原则：** 开闭原则
- **描述：** 部分 routing/classification 行为仍依赖原始字符串匹配。`skill_mcp_mapping_registry` 的注释显示它已经从 product-name 分支迁移到 mapping entry，这是正确方向。剩余分类逻辑也应继续向数据驱动 descriptor 和 typed capability metadata 演进。
- **证据：** 静态扫描发现 `command.contains(pattern)` 和多个关键词链。
- **建议：** 优先使用声明式 descriptor、versioned mapping file 和 typed capability tag。字符串匹配只保留在 ingestion boundary，并确保可审计。

## 依赖图分析

Cargo workspace 包含 27 个成员。观察到的依赖方向整体符合预期分层：

- Foundation：`macaca-proto`、`macaca-ipc`、`macaca-persist`
- Kernel：`macaca-kernel`
- Services：context、llm、memory、tools、task、scheduler、heartbeat、driver、skill、gateway、autonomy
- Runtime：`macaca-runtime`、`macaca-runtime-host`、`macaca-framework`、`macaca-host-composition`
- Application：`macaca-agent`、`macaca-app`
- Facade：`macaca-sdk`
- Shells：`macaca-web`、`macaca-cli`
- Integration gates：`macaca-integration-tests`

未发现明显证据表明 kernel 依赖 presentation shell。主要耦合热点集中在预期的组合点：runtime-host、web shell state/composition、SDK clients。因此当前 smell 主要是**残余所有权密度**，不是循环依赖式架构坍塌。

## 重构路线图

### 立即行动

1. 将 `macaca-web` 中的 task decomposition 关键词逻辑迁移到 service-owned decomposition strategy 或 command。
2. 将 `serviceization_escape_hatches.rs` 拆分为更小的策略分类边界 gate。
3. 增加生产 Rust 文件 450 行软警告。
4. 增加静态检查，禁止 shell 层新增 task/planning 语义，除非它只是调用 SDK/facade client。

### 短期行动

1. 将接近上限的 runtime-host provider 按 `descriptor`、`state`、`commands`、`handler`、`tests` 拆分。
2. 在 capability catalog、route projection、task dependencies、skill mappings 中为重复 membership scan 建立局部索引。
3. 为 `OnceLock` / static registry 增加模块级 ownership 注释。
4. 将重复 test fixture 抽到小型 support module，避免继续膨胀 integration test 文件。

### 长期行动

1. 对成熟的 runtime-host provider family，在契约稳定后评估是否提取为独立 service crate。
2. 按 command family 拆分 `macaca-proto` DTO 模块，并避免 protocol object 承载业务行为。
3. 将剩余文本/名称驱动路由替换为 typed capability descriptor、声明式 mapping 和可审计 fallback policy。
4. 引入自动化 architecture-smell CI lane，初期只报告 complexity 和 coupling 趋势，不直接 fail。
